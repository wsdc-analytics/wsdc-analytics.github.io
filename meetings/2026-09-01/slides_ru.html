Core Встреча · analytics committee

Points Registry и аналитика board:
что видно снаружи, чего не хватает

Разбор того, что реально даёт публичный реестр, где правила уже просят больше данных, и что нужно упорядочить в процессах, чтобы отвечать на вопросы комитета.

Core Зачем этот разговор

Что хотим получить с созвона

По делу

  • Сверить: какие данные есть публично, какие уже сдаются по правилам, какие реально хранятся
  • Привязать повестку board к ограничениям этих данных
  • Согласовать, какие процессы чинить в первую очередь

Не сегодня

  • Не разбор «плохой базы». Речь о том, что видно при глубокой работе с открытым registry
  • Сначала общая рамка данных и процессов; как именно внедрять инструменты решает комитет
  • Не обещание готовых цифр по всем вопросам board до сверки источников

На полях: на WSDC Analytics уже есть аналитика на публичных данных. Это пример того, что можно сделать снаружи, не требование к комитету.

Core 1 · Инвентарь

Что даёт публичный Points Registry

Официальная запись результатов WSDC Jack & Jill на Registry Events. Снаружи это в основном истории танцоров с поинтами.

Есть

  • Танцоры с WSDC Competitor ID и начисленными поинтами
  • Издания ивентов и scored-результаты по номинациям
  • Tier как сигнал размера дивизиона×роли (диапазон, не точный headcount)
  • Календарь / список registry events (отдельно от «кто вышел на паркет»)

В открытом слое нет

  • Полного стартового листа номинации в удобном для аналитики виде
  • Танцоров, которые участвовали, но так и не получили поинт
  • «Чистой» географии без ручной нормализации имён и локаций

Источник определения registry: WSDC Registry Event Rules 2026.1B, Overview / Points Registry.

Core 1 · Инвентарь

Что правила уже просят сдавать

По §2.3 Competitor Results Reporting члены сдают результаты всех WSDC J&J. Живой носитель — workbook Score Report (v2026.1B): там уже заложено больше, чем видно в публичном lookup.

  • Все petitions
  • WSDC ID финалистов (если ID уже выдан)
  • Число конкурентов в каждом дивизионе (для Tier)
  • List of all competitors registered — лист Score Report Competitors List
  • Плюс лист Dual / Multiple Roles для тех, кто танцевал в двух ролях

Вопрос не «надо ли собирать списки»

Листы уже есть. Открытые вопросы: обязательные колонки (нужен ли WSDC ID в каждой строке, включая тех, у кого ещё нет поинтов?), машиночитаемый формат, и уходят ли сданные xlsx только с протоколами ивента или попадают в рабочую базу, которую можно стыковать с Points Registry.

Registry Event Rules 2026.1B §2.3 (items 1-4); Score Report Form v2026.1B на WSDC Forms. Срок сдачи: не позднее 3 дней после закрытия ивента.

Core 2 · Повестка board

Четыре направления из запроса комитета

  1. Competitor base 2021-2026: сколько танцоров по skill levels; community overall; по возможности регион
  2. Points & tiers: текущая структура, влияние изменений; прогрессия большинства (много поинтов у небольшого меньшинства)
  3. Event landscape & capacity: где рост обоснован (организатор на месте + case территории); когда ограничивать новые ивенты; аналитика подтверждает сигналы спроса
  4. Point structure: как проверить данными, нужно ли менять структуру поинтов

Дальше не цифры, а карта: что мешает ответить прямо и что чинить в процессах.

Core Мост

От повестки к четырём разрывам

Без общих определений «танцора», «участника», «региона» и «ивента» отчёты board будут спорить сами с собой. В открытом registry четыре системных дыры.

A. Identity

ID появляется после первого поинта. До этого человека нет в registry как сущности.

B. Coverage

Публичный слой = scored history. Полные списки уже в листах Score Report — формат и retention неясны.

C. Data quality

Free-text intake в Event Update / New Event Application / Score Report: варианты имён, пустые локации, «плывущие» серии.

D. Geo / landscape

Capacity — не упражнение на карте: организатор на месте, case территории, затем аналитика для подтверждения спроса.

Core Gap A · Identity

ID выдаётся только после поинта

Это не догадка по данным. В правилах прямо сказано: Competitor ID назначается только после того, как танцор получил поинт.

  • До первого поинта человека нет в Points Registry как отслеживаемой сущности
  • Можно много раз выйти на паркет и остаться невидимым для публичной аналитики
  • «Сколько танцоров в community» и «сколько уникальных WSDC ID с поинтами» это разные метрики

Registry Event Rules 2026.1B §3.2.2c; Overview: ID after at least one J&J point.

Core Gap A · Влияние

Как это бьёт по повестке

По вопросам board

  • Q1: занижение «активных», особенно Newcomer и Novice
  • Q2: воронка входа обрезана до тех, кто уже получил поинт
  • Q3: спрос новичков почти не виден в registry

Что делать в процессах

  • Зафиксировать политику: ID только после поинта (как сейчас) или раньше
  • Если оставляем «после поинта», в отчётах писать scored population, не «вся community»
  • Для полной популяции опираться на Score Report Competitors List / Dual Roles (§2.3) — когда ясны формат и retention
Core Gap B · Coverage

Публичный registry ≠ полный entry list

Снаружи мы видим в основном тех, кому начислили поинты. Полный список зарегистрированных уже собирается в workbook Score Report — листы Competitors List и Dual / Multiple Roles — но в открытом Points Registry его нет.

Видно снаружи

  • Строки с поинтами / история ID
  • Косвенно: Tier по размеру дивизиона×роли

Собирается в Score Report, снаружи нет

  • Все зарегистрированные в J&J (Competitors List)
  • Участники dual / multiple roles
  • Точный headcount и доля без поинтов — только если списки хранятся и стыкуются

Tier помогает оценить порядок масштаба. Он не заменяет именной entry list с ясной схемой (включая как оформлять WSDC ID у тех, кто ещё без поинтов).

Core Gap B · Влияние

Влияние и путь вперёд

По вопросам board

  • Q1: skill counts по registry = scored, не starters
  • Q2: нельзя отделить «мало танцуют» от «не доходят до поинтов»
  • Q3-Q4: capacity и сценарии смены поинтов без воронки остаются хрупкими

Процессный путь (листы Score Report)

  • Зафиксировать схему листа: обязательные поля, как вводить WSDC ID, если ID ещё нет
  • Проследить путь после сдачи: остаётся xlsx с протоколами ивента или загружается в базу?
  • Если сегодня только файлы — спроектировать рабочее хранилище, чтобы списки стыковались с Points Registry
Core Gap C · Data quality

Качество сущностей: что всплывает в открытых данных

При глубокой работе с registry регулярно встречаются расхождения имён и локаций. Это следствие free-text intake в существующих формах WSDC, а не «злой умысел».

1. Разные названия одной серии
В календаре: Asia WCS Open XI, Asia WCS Open XIII, Asia WCS Open - 10th Anniversary. Канон: Asia WCS Open. Без словаря синонимов ряды ломаются.
2. Пустая локация в выгрузке результатов
У Scandinavian Open в локальном extract результатов поле локации пустое во всех 993 строках. Гео приходится восстанавливать из других источников.
3. Варианты написания бренда
St.Petersburg WCS Nights / Saint Petersburg WCS Nights; Vestigala / Westie Gala. Без aliases появляются ложные «новые» ивенты.
4. Одно имя, разные истории
Spring Swing: Stockholm и Detroit. Sunny Side Dance Camp: Crimea, затем Torrevieja. Нужны правила «сливать / не сливать».

Откуда входит: Event Update и New Event Application принимают название ивента и локацию free text; Score Report Info Summary — то же для Event Name / Location. Набор с пустой формы → новые aliases и новые написания гео.

Core Gap C · Локации

Мусор в локациях: зачем нужна стандартизация

Одни и те же поля пишутся по-разному. Ниже только маленькая часть примеров из открытых данных; таких строк в registry намного больше.

Предлагаемое решение

Центральные справочники ивентов и локаций (canonical name; для US — ещё штат). Затем правим существующие формы: Event Update выбирает ивент и prefills; New Event Application / Score Report берут локацию из справочника — free text остаётся для контактов и ops по venue, не для entity-полей.

Core Gap C · Влияние

Почему без DQ нельзя «просто посчитать»

Что ломается

  • Ряды по ивентам и странам
  • Двойной счёт или «пропавшие» издания
  • Региональные выводы board
  • Любая автоматизация без master-данных копирует мусор

База решения

  • Справочник ивентов: одно canonical name / один ID
  • Справочник локаций: city + country в одном формате (для американских ивентов — ещё штат)
  • Формы оргов: Event Update / New Event / Score Report на справочниках
  • Орги отвечают за актуальность своих записей
Core Gap C · Регламент

Изменения в справочник только заранее и по правилам

Организаторы обязаны следить за своими ивентами и локациями в справочнике. Любое изменение существующих данных или создание нового ивента подаётся предварительно — затем Event Update и Score Report могут выбирать только то, что уже есть в справочнике.

В регламенте прописать типы изменений

  • Новый ивент (через New Event Application) → новый ID + canonical name в справочнике
  • Переименование серии (старое имя → alias / история)
  • Смена локации (город/страна; для US — ещё штат)
  • Исправление ошибки в справочнике

Как формы это закрепляют

  • Event Update: выбрать существующий ивент → prefill; без набора name/location с пустой формы
  • Score Report: Event Name / Location из справочника или Event ID
  • Free text OK: контакты, ops по venue, ownership, shuttle
  • Без записи в справочнике нельзя выбрать ивент/локацию в форме

Иначе снова появятся free-text варианты вроде USA / US / United States и «новые» ивенты-переименования — именно это сегодня допускают пустые поля Event Update / Score Report.

Core Gap D · Landscape

Landscape и capacity: сначала организатор

WSDC не проводит ивенты. Организаторы запрашивают трайлы и новые ивенты, тратят деньги и несут риск, что ивент окупится. «Белого пятна» на карте недостаточно — нужен организатор на месте и обоснованный case для этой территории.

Организатор в процессе

  • Именованный организатор берёт операционную и финансовую ответственность
  • Трайл / новый ивент: краткий case территории (New Event Application уже спрашивает viability — сохранить и структурировать)
  • Сверка с текущей сеткой ивентов (перегруженный регион vs один крупный ивент и растущая сцена)

Где помогает аналитика

  • Подтверждает косвенные сигналы: загрузка entry на соседних ивентах, плотность в регионе, scored-активность
  • Не заменяет план организатора и не гарантирует окупаемость
  • Ограничения остаются: город ивента ≠ дом танцора; плохая гео рисует ложные «дыры»
Core Gap D · Влияние

Влияние и процессный путь

Риск для Q3-Q4

  • Решения по карте или «на ощущениях», без организатора на месте и case территории
  • Одобрить ещё один ивент в перегруженном регионе без проверки мотивации
  • Менять point structure без модели воронки

Что зафиксировать

  • Структурировать New Event Application как case территории (+ подтверждение аналитикой); name/location не free text
  • Стабильная гео ивентов + entry counts/lists как слой аналитики рядом с Tier
  • Три метрики отдельно: event supply, scored demand, entry demand
Core Сводка

Матрица: что можно ответить на публичных данных

Вопрос board Сейчас (публичный registry) Что разблокирует полный ответ
Competitors by skill 2021-2026 (+ region) Частично уникальные ID с поинтами; регион слабо / через proxy ивентов Хранение/стыковка Score Report Competitors List (+ Dual Roles) + политика ID + чистая гео
Points/tiers & progression majority Частично распределение поинтов и переходы по scored; воронка входа обрезана Entries + явное определение «majority»

На одном только публичном registry ни один пункт не закрывается полностью. Это нормально зафиксировать вслух.

Core Финал

Checklist: что упорядочить

  1. Инвентаризация: куда уходят файлы Score Report Competitors List / Dual Roles после сдачи, за какие годы они ещё есть
  2. Схема списка: обязательные колонки; как оформлять WSDC ID, если у танцора ещё нет ID
  3. Хранилище: только xlsx с протоколами или база, которую можно стыковать с Points Registry?
  4. Правило ID: оставляем «только после поинта» или меняем; как подписывать метрики
  5. Справочники + формы: Event Update prefills; New Event Application / Score Report без free-text у name & location
  6. Словарь метрик board: scored population vs entry population vs community
  7. Trial / new events: структурировать case, уже заложенный в New Event Application; сверка с сеткой ивентов
Core Discovery

Четыре вопроса на сверку

  1. После сдачи Score Report: листы Competitors List / Dual Roles остаются xlsx с протоколами ивента или попадают в центральное хранилище?
  2. За какие годы (хотя бы 2021-2026) эти списки ещё восстановимы?
  3. Что обязательно в каждой строке списка сегодня — нужен ли WSDC ID, если у танцора ещё нет поинтов?
  4. Кто владеет процессом intake для Event Update / New Event Application / Score Report и кто может его менять?

Закрытие: на публичных данных уже можно делать осторожную аналитику. Устойчивые ответы board появятся, когда списки Score Report станут рабочим слоем, а Event Update перестанет плодить free-text drift имён/локаций. Инструменты комитет выбирает сам.

Appendix

Детали, если на созвоне будет время.

Appendix Q1

Competitors by skill / region

Можно сейчас

  • Уникальные ID с поинтами по годам
  • Разрезы по дивизионам scored-результатов
  • Грубая гео через локацию ивентов (proxy)

Нельзя честно назвать community

  • Участники без поинтов
  • Точный home region танцора
  • Newcomer funnel до первого поинта
Appendix Q2

Points, tiers, progression majority

  • Можно: концентрация поинтов, скорость набора, переходы по scored; сравнения до/после смены правил
  • Осторожно: «majority» нужно определить (все ID? активные за год? ≥N поинтов?)
  • Нужно: entry-данные, чтобы отделить «нет поинтов» от «не участвовали»
Appendix Q3

Event landscape & capacity

  • Сначала процесс: организатор на месте + краткий case территории; WSDC проверяет мотивацию, не организует сам
  • Можно: число registry events, география, динамика 2021-2026, региональная загрузка entry (когда есть lists)
  • Частично: подтвердить спрос через travel scored, плотность ивентов, регистрации на соседних ивентах
  • Не решает сама: окупится ли ивент для организатора
Appendix Q4

Point structure change

  • Можно: сценарные пересчёты на scored истории; чувствительность топов и порогов
  • Риск: оптимизация под тех, кто уже в registry, без модели входа
  • Сначала KPI: рост majority, честность порогов, нагрузка на оргов
Appendix Tiers

Tier = диапазон размера, не точный счёт

В правилах Tier зависит от числа уникальных конкурентов в дивизионе×роли. По публичным данным можно суммировать границы диапазонов. Это оценка порядка, не headcount.

  • Удобно сравнивать масштаб ивентов
  • Не заменяет именной entry list из §2.3
  • Открытый верх у старших tier нужно помечать как неопределённость
Appendix Определения

Три популяции. Не смешивать в одном отчёте

Scored population

Уникальные WSDC ID с поинтами за период. То, что даёт публичный Points Registry.

Entry population

Все зарегистрированные в WSDC J&J. Уже заложены в §2.3 reporting, нужны в хранении.

Community (широко)

Включает тех, кто вне scored-исходов и, возможно, вне registry events. Отдельная методология.

Практика

В каждом отчёте board подписывать, какая популяция использована.
