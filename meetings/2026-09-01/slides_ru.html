Core Встреча · analytics committee

Points Registry и аналитика board:
что видно снаружи, чего не хватает

Разбор того, что реально даёт публичный реестр, где правила уже просят больше данных, и что нужно упорядочить в процессах, чтобы отвечать на вопросы комитета.

Core Зачем этот разговор

Что хотим получить с созвона

По делу

  • Сверить: какие данные есть публично, какие уже сдаются по правилам, какие реально хранятся
  • Привязать повестку board к ограничениям этих данных
  • Согласовать, какие процессы чинить в первую очередь

Не сегодня

  • Не разбор «плохой базы». Речь о том, что видно при глубокой работе с открытым registry
  • Сначала общая рамка данных и процессов; как именно внедрять инструменты решает комитет
  • Не обещание готовых цифр по всем вопросам board до сверки источников

На полях: на WSDC Analytics уже есть аналитика на публичных данных. Это пример того, что можно сделать снаружи, не требование к комитету.

Core 1 · Инвентарь

Что даёт публичный Points Registry

Официальная запись результатов WSDC Jack & Jill на Registry Events. Снаружи это в основном истории танцоров с поинтами.

Есть

  • Танцоры с WSDC Competitor ID и начисленными поинтами
  • Издания ивентов и scored-результаты по номинациям
  • Tier как сигнал размера дивизиона×роли (диапазон, не точный headcount)
  • Календарь / список registry events (отдельно от «кто вышел на паркет»)

В открытом слое нет

  • Надёжного forward-сигнала, что edition этого года состоится (в правилах confirmed — post-event Update Form)
  • Полного стартового листа номинации в удобном для аналитики виде
  • Танцоров, которые участвовали, но так и не получили поинт
  • «Чистой» географии без ручной нормализации имён и локаций

Источник определения registry: WSDC Registry Event Rules 2026.1B, Overview / Points Registry.

Core 1 · Инвентарь

Что правила уже просят сдавать

По §2.3 Competitor Results Reporting члены сдают результаты всех WSDC J&J. Живой носитель — workbook Score Report (v2026.1B): там уже заложено больше, чем видно в публичном lookup.

  • Все petitions
  • WSDC ID финалистов (если ID уже выдан)
  • Число конкурентов в каждом дивизионе (для Tier)
  • List of all competitors registered — лист Score Report Competitors List
  • Плюс лист Dual / Multiple Roles для тех, кто танцевал в двух ролях

Вопрос не «надо ли собирать списки»

Листы уже есть. Открытые вопросы: обязательные колонки (нужен ли WSDC ID в каждой строке, включая тех, у кого ещё нет поинтов?), машиночитаемый формат, и уходят ли сданные xlsx только с протоколами ивента или попадают в рабочую базу, которую можно стыковать с Points Registry.

Registry Event Rules 2026.1B §2.3 (items 1-4); Score Report Form v2026.1B на WSDC Forms. Срок сдачи: не позднее 3 дней после закрытия ивента.

Core Рамка

Три популяции. Не смешивать в одном отчёте

Вопросы board смешивают эти слои, если не назвать, о каком именно речь.

Community (широко)

Люди вне scored-исходов и, возможно, вне registry events.

Источник: отдельная методология — не только Points Registry

Entry population

Все зарегистрированные в WSDC J&J. Уже собираются в листах Score Report.

Источник: Competitors List / Dual Roles — нужны схема и retention

Scored population (публичный)

Уникальные WSDC ID с поинтами. То, что видно в открытом Points Registry.

Источник: публичный lookup / scored history
Core 2 · Повестка board

Четыре направления из запроса комитета

  1. Competitor base 2021-2026: сколько танцоров по skill levels; community overall; по возможности регион
  2. Points & tiers: текущая структура, влияние изменений; прогрессия большинства
  3. Event landscape & capacity: где рост обоснован (организатор на месте + case территории); когда ограничивать новые ивенты
  4. Point structure: как проверить данными, нужно ли менять структуру поинтов

Дальше — карта ограничений, не цифры board.

Core Мост

От повестки к четырём разрывам

Без общих определений «танцора», «участника», «региона» и «ивента» отчёты board будут спорить сами с собой.

A. Identity

ID появляется после первого поинта. До этого человека нет в registry как сущности.

B. Coverage

Публичный слой = scored history. Полные списки в Score Report — формат и retention неясны.

C. Data quality

Free-text intake в Event Update / New Event Application / Score Report плодит drift имён и локаций.

D. Landscape / calendar

Capacity нужен организатор на месте и case территории; аналитика только подтверждает спрос. В правилах нет forward-подтверждения в календаре WSDC.

Core Gap A · Identity

ID только после поинта — и что из этого следует

По правилам Competitor ID назначается только после поинта. До этого человека нет в публичном Points Registry.

Бьёт по повестке

  • Counts: занижение «активных», особенно Newcomer и Novice
  • Progression: воронка входа обрезана до тех, кто уже получил поинт
  • Capacity: спрос новичков почти не виден в registry

Что делать в процессах

  • Оставить «ID после поинта» или менять — в любом случае честно подписывать отчёты
  • Если после поинта: писать scored population, не «вся community»
  • Полная популяция — через листы Score Report, когда ясны схема и retention

Registry Event Rules 2026.1B §3.2.2c.

Core Gap B · Coverage

Списки собираются — ещё не рабочий слой аналитики

В Score Report уже есть Competitors List и Dual / Multiple Roles. Публичный registry по-прежнему показывает в основном тех, кто получил поинт. Открыты вопросы формата, ID и куда уходят файлы после сдачи.

Почему важно

  • Counts: skill counts по registry = scored, не starters
  • Progression: нельзя отделить «мало танцуют» от «не доходят до поинтов»
  • Capacity / point structure: без воронки входа остаются хрупкими

Что зафиксировать

  • Схема листа: обязательные поля; как вводить WSDC ID, если ID ещё нет
  • Путь после сдачи: только xlsx с протоколами или хранилище со стыковкой к Points Registry?
  • Если сегодня только файлы — спроектировать это хранилище
Core Gap C · Data quality

Качество сущностей: что всплывает в открытых данных

Расхождения имён и локаций — следствие free-text intake в существующих формах WSDC, а не «злой умысел».

1. Разные названия одной серии
Asia WCS Open XI, XIII, 10th Anniversary → канон Asia WCS Open. Без aliases ряды ломаются.
2. Пустая локация
Scandinavian Open: пустая локация во всех 993 строках локального extract.
3. Варианты написания бренда
St.Petersburg / Saint Petersburg WCS Nights; Vestigala / Westie Gala.
4. Одно имя, разные истории
Spring Swing: Stockholm и Detroit. Sunny Side Dance Camp: Crimea, затем Torrevieja.

Откуда входит: Event Update, New Event Application и Score Report Info Summary принимают название и локацию free text. Набор с пустой формы → новые aliases и написания гео.

Core Gap C · Локации

Мусор в локациях: зачем нужна стандартизация

Одни и те же поля пишутся по-разному. Маленькая выборка из открытых данных.

Core Gap C · Решение

Справочники + формы, которые их закрепляют

Без master-данных ломаются ряды по ивентам и странам, издания двоятся или пропадают, автоматизация копирует мусор. Правим существующие формы — не изобретаем параллельный paper trail.

Справочники

  • Ивенты: одно canonical name / один ID
  • Локации: city + country (для US — ещё штат)
  • Типы изменений заранее: новый ивент, rename, смена локации, правка ошибки
  • Орги отвечают за актуальность своих записей

Как формы это закрепляют

  • Event Update: выбрать ивент → prefill; без набора name/location с пустой формы
  • New Event Application: после approval → новая строка справочника
  • Score Report: Event Name / Location из справочника или Event ID
  • Free text OK: контакты, ops по venue, ownership, shuttle
Core Gap D · Landscape

Landscape и capacity: сначала организатор

WSDC не проводит ивенты. «Белого пятна» на карте недостаточно — нужен организатор на месте, который несёт риск, и обоснованный case территории.

Организатор в процессе

  • Именованный организатор берёт операционную и финансовую ответственность
  • Структурировать case, уже заложенный в New Event Application (viability + сверка с сеткой)
  • Перегруженный регион vs один крупный ивент и растущая сцена — разные решения

Где помогает аналитика

  • Подтверждает сигналы спроса: entry на соседних ивентах, плотность, scored-активность
  • Не заменяет план организатора и не гарантирует окупаемость
  • Name/location не free text; отдельно: supply, scored demand, entry demand
Core Gap D · Календарь

Календарь ивентов: «confirmed» только после проведения

WSDC Events calendar — публичный список registry events — но правила требуют post-event подтверждения. По одним источникам WSDC community не может понять, состоится ли edition этого года, пока ивент не прошёл (или не объявлен hiatus).

Что в правилах сейчас (2026.1B)

  • §1.1.4: Registry Event Update Form — в течение 45 дней после закрытия → confirmed в WSDC Events calendar
  • §1.3.2: Trial — list on WSDC website после одобрения Board (без срока в днях до ивента)
  • §1.1.9: за 90 дней — rules и schedule на сайте организатора, не в календаре WSDC
  • Нет требования опубликовать edition этого года в календаре WSDC до даты ивента

Почему это больше, чем аналитика

  • «Confirmed» появляется задним числом — слабый сигнал для travel, trial и сверки сетки
  • До hiatus (6 месяцев notice) или post-event Update — только догадка по прошлому году
  • У trial-оргов нет одного публичного view, что реально запланировано в регионе

Изменение правил — обсудить

Требовать подтверждение upcoming edition в календаре WSDC к фиксированной дате до ивента (горизонт выбирает комитет — например, стыковка с 6-месячными окнами change/hiatus). Разделить статусы: scheduled / confirmed will run / hiatus or cancelled / confirmed ran. Питать через Event Update + event directory, чтобы календарь, Time/Distance и аналитика брали один источник.

Registry Event Rules 2026.1B §1.1.4, §1.3.2, §1.4, §1.5; WSDC Events calendar.

Core Финал

Что упорядочить — и три вопроса

Checklist

  1. Листы Score Report: схема (в т.ч. WSDC ID, если ID ещё нет) + куда уходят файлы после сдачи
  2. Правило ID: оставляем «только после поинта» или меняем; как подписывать метрики
  3. Справочники + формы: Event Update prefills; без free-text name/location
  4. Словарь метрик: scored vs entry vs community
  5. Trial / new events: структурировать case New Event Application vs сетка ивентов
  6. Правила календаря: pre-event confirmation + модель статусов (scheduled / will run / hiatus / ran)

Спросить на созвоне

  1. После сдачи Score Report: только xlsx с протоколами или центральное хранилище?
  2. Должен ли Update Form подтверждать upcoming edition до ивента — а не только после закрытия?
  3. За 2021-2026 Competitors List / Dual Roles ещё восстановимы?
  4. Кто владеет intake Event Update / New Event Application / Score Report — и кто может менять правила календаря?

Закрытие: на публичных данных уже можно делать осторожную аналитику. Устойчивые ответы board нуждаются в списках Score Report как рабочем слое и Event Update без free-text drift имён/локаций. Инструменты комитет выбирает сам.
