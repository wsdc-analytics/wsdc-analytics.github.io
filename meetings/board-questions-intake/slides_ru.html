Как принимать вопросы Board,
не раздувая не ту работу

Общий способ классифицировать запросы по готовности данных компании WSDC: отвечаем сейчас (полностью или частично), данные есть, но ещё не в аналитическом стриме, данные внутри WSDC ещё не собирали, данные вне WSDC — и governance, который не датасет.

Scope Зачем классифицировать

Лучше текущая работа — не больше тарелка

Вопросы Board приходят смешанными. Без рамки каждый выглядит как «ещё аналитика», и комитет уезжает в новые продуктовые фронты, пока инфраструктура и mission-работа всё ещё нуждаются в поддержке.

Постоянное правило (Kay)

Использовать комитет, чтобы усиливать текущие инициативы Board и инфраструктуру. По умолчанию не расширять scope на новые хабы, эксперименты с платой и ownership сборки — пока Board явно не поручит.

Что даёт классификация

  • Дробит одно сообщение на атомарные вопросы
  • Называет слой данных для каждого атома
  • Отделяет deliverables от enabling-работы и от решений по scope
Frame Популяции

Три популяции. Не смешивать

Community

Широкий мир WCS: social и обучение — в основном вне реестра.

Entry

Все зарегистрированные в WSDC J&J. Уже запрошены в списках Score Report (§2.3) — для аналитики нужны retention и join.

Scored

Люди с начисленными поинтами / Competitor ID после поинта. Это то, что публичный реестр поддерживает сегодня.

Competitor ID только после поинта — Rules 2026.1B §3.2.2c. Согласовано с analytics brief от 1 сентября.

Model Категории

Как мы раскладываем вопросы Board

Не «хорошая / плохая база», а готовность данных компании (WSDC) к ответу. Личная аналитическая база здесь ни при чём.

C1

Можно отвечать сейчас

Данные уже в рабочем стриме (Points Registry, каталог ивентов). Часть вопросов — полностью; часть — частично (обычно только Scored), если спрашивающего это устраивает.

C2

Данные в контуре WSDC есть — в стрим ещё нельзя

Уже собираются (часто через Google Sheets / Score Report), но не нормализованы, не почищены, нет пайплайна. Нужна доработка: схема, алиасы, join, retention — чтобы сделать пригодными для аналитики.

C3

В контуре WSDC, но пока не собирали

Предполагаем, откуда взять (внутри WSDC). Пока сырого потока нет. Сначала научиться брать → затем это станет C2.

C4

Вне WSDC

Локальные танцы, воркшопы, non-WSDC weekends, опросы. Когда данные начнут собирать — попадают в C2 (есть, но ещё не в общем строе).

C5

Другой круг: scope / governance

Приоритеты, product, политика, fee — не датасет. К пайплайну C1–C4 почти не относится.

C1 Можно отвечать сейчас

Рабочий стрим — аналитика уже возможна

Points Registry и каталог ивентов регулярно обновляются. Полный ответ, где ask укладывается в Scored; частичный — если спрашивающего устраивает этот слой.

Что есть

  • Поинты / размещения / Competitor ID после поинта
  • Каталог ивентов и scored-ландшафт YOY
  • Готовая C1-работа (напр. переходы дивизионов)

Ограничения

  • Scored ≠ Entry / attendance / «held»
  • Partial надо явно маркировать — не «вся community»
  • Invitational / no-shows из реестра одними не закрыть

Quality на этом слое

  • Меньше free-text; стандартизация сущностей
  • Регулярные таблицы: танцор · ивент · результат
  • Качество WSDC-слоя — не спор «чья база»

Отдавать сейчас: прогрессия / структура поинтов · scored-ландшафт ивентов · пути Champions и inactivity (с оговорками).

C2 Есть — не в стриме

Уже в контуре WSDC — ещё не стыкуется

В Score Report / Sheets уже есть зачатки (часто с ~2023). Можно проектировать, как они войдут в общий аналитический стрим рядом с C1.

Что уже есть

  • Отчёты ивентов: тиры, counts по номинациям / ролям
  • Competitors List — проблемный, но след есть
  • Тот же контур, что требования списков §2.3

Ограничения

  • Глубина в основном с ~2023
  • Нет устойчивой схемы / retention / join ID
  • Пока не садится в общий DWH/стрим рядом с C1

Путь → C1

  • Pipeline: ingest → clean → сущности → join к C1
  • Алиасы geo / имён ивентов (Gap C)
  • Архив до 2023 / пропуски → часто сначала C3, потом C2

List участников ещё зачаток: практический добор — scoring-системы. Текущие частичные фиды остаются C2, пока не joinable.

C3 В контуре — ещё не брали

Полагаем, что лежит в WSDC — пока не забирали

По вопросам Board: к кому идти внутри WSDC, что запросить, можно ли взять. Часто — архив / обогащение того же блока, что C2.

Типичные пробелы

  • Глубина Score Report / списков до 2023
  • Home city/state, official dates, потоки судей AJP
  • Поля где-то в ops — не в нашем стриме

Работа сейчас

  • Найти владельца и формат внутри WSDC
  • Подтвердить: можно ли получить и на каких правилах
  • Не выдавать за уже готовое к аналитике

Дальше — повышение

  • Нашли и можно брать → C2
  • Pipeline + join → C1
  • Не нашли / вне контура → пересмотр (C4 / парк)
C4 Вне WSDC

Локальный мир WCS — не контур реестра

Воркшопы, локальные танцы, non-WSDC weekends, популяция WCS вокруг ивентов (напр. JN-3c). Здесь старт — дизайн сбора, не extract из Points Registry.

Что это

  • Community-ландшафт вне ивентов WSDC
  • Радиус от venue / локальная популяция
  • Точность не будет registry-grade

Как организовать

  • Начать с уже собранных community-хабов (примеры ниже), затем закрывать дыры
  • Возможно regional leads из других комитетов
  • Сектора / регионы + cadence проверки; владелец и мандат Board

Дальше

  • Когда поток есть → C2
  • Комитет советует схему — не забирает тихо сайт / fee
  • Product / fee / hub-политика → C5

Примеры уже централизованных community-листингов (не WSDC, не registry-grade): weekenders.dance · westiehub.dance

C5 Scope / governance

Это не вопрос пайплайна данных

Отделить аналитику и enablement от стратегии, продукта и политики — чтобы комитет не съел чужую работу (фильтр Kay).

Что это

  • Приоритеты, мандат, растягивание mission
  • Сайт / product (напр. рейтинги на сайте)
  • Fee, merge/delete, политика аудита

Примеры в этом драфте

  • Идеи hub / education-расширения
  • NEA «ideas for analytics» как initiative
  • Listing fees, product-фильтры на сайте

Что делаем

  • Вернуть Board / ops с ясной рекомендацией
  • Можно советовать на C1-evidence — не владеть product
  • Не поднимается по лестнице C3 → C2 → C1
Logic Трансформация

Как вопросы двигаются по мере готовности данных

C3 · ещё не брали

Есть гипотеза, где в WSDC лежат данные. Проработать: к кому идти, можно ли взять, в каком виде.

C4 · вне WSDC

Community-сбор. Когда поток появится — тоже в C2.

научиться брать / собирать →

C2 · есть, но не в строе

Короткий перечень: что получить и чему научиться (пайплайн, join, очистка). После этого вопросы уходят в C1.

→ научиться работать со стримом →

C1 · отвечаем

Полный ответ или частичный (если устраивает). C2/C3 по мере enablement схлопываются сюда.

C5 · отдельно

Стратегия и ownership — не этап этой лестницы.

Развилка C3 / C4 → обе кормят C2. Дальше C2 → C1. Матрица вопросов — следующий шаг: кто в какой клетке сейчас.

Process Процесс

От вопроса к трекингу

  1. Приём — кто спросил, текст, must-have vs nice-to-have
  2. Декомпозиция — одно сообщение Board → несколько атомарных вопросов
  3. Классификация — C1–C5 + популяция (Community / Entry / Scored)
  4. Ответ — отдать (C1), частичный ответ + enabling-шаг (C2/C3), дизайн сбора (C4) или вернуть по scope (C5)
  5. Трекинг и переклассификация — когда enabling-шаг сделан

Внутренние детали: meetings/board-questions-intake/CONCEPT.md и MATRIX.md.

C1 делится на полный ответ (брать сейчас) и частичный (та же цитата Board, Scored / ограниченный слой). Entry / списки — в C2 с конкретным шагом. Это задуманный split, не провал реестра.

Ask Приоритеты Board

Что нужно от Board

  1. Подтвердить рамку intake 4+1 (включая правило Kay по scope)
  2. Выбрать один C2/C3 enablement на квартал (рекомендация: retention + схема списков Score Report)
  3. Назначить владельца, если C4 community listings становятся программой Board
  4. Оставить website / merge-delete / fee на governance-треке — комитет может советовать с опорой на C1
