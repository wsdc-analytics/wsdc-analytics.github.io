Brief Analytics committee · Board intake

How we take Board questions
without expanding the wrong work

A shared way to classify asks by WSDC company data readiness: answerable now (full or partial), data that exists but isn’t in the analytics stream yet, data we believe we can collect inside WSDC, data outside WSDC — and governance that isn’t a dataset.

Scope Why classify

Better current work — not a bigger plate

Board asks arrive mixed. Without a frame, every ask looks like “more analysis,” and the committee drifts into new product fronts while infrastructure and mission work still need support.

Standing rule (Kay)

Use this committee to make current Board initiatives and infrastructure stronger. Default against expanding scope into new hubs, fee experiments, or build-ownership unless the Board mandates it.

What classification does

  • Splits one message into atomic questions
  • Names the data layer each atom needs
  • Separates deliverables from enabling work and from scope decisions
Frame Populations

Three populations. Do not mix them

Community

Broader WCS social and learning world — mostly outside the registry.

Entry

Everyone registered in WSDC J&J. Already requested in Score Report lists (§2.3) — usable analytics need retention and join.

Scored

People with awarded points / Competitor ID after a point. This is what the public registry supports today.

Competitor ID only after a point — Rules 2026.1B §3.2.2c. Aligns with the 1 September analytics brief.

Model Categories

How we sort Board questions

Not “good vs bad database” — how ready WSDC company data is to answer. This is not about a personal analytics store.

C1

Answerable now

Already in a working stream (Points Registry, event catalog). Some asks fully; some only partially (usually Scored) — if that works for the asker.

C2

Data exists in WSDC — not in the analytics stream yet

Already collected (often Google Sheets / Score Report), but not normalized or cleaned, no pipeline. Need company-side prep: schema, aliases, join, retention — to make it usable.

C3

Inside WSDC contour — not collected yet

We believe where to get it inside WSDC. No raw stream yet. First learn to collect → then it becomes C2.

C4

Outside WSDC

Local dances, workshops, non-WSDC weekends, polls. Once collected, those feeds land in C2 (exist, not yet in the shared pipeline).

C5

Separate circle: scope / governance

Priorities, product, policy, fees — not a dataset. Outside the C1–C4 readiness ladder.

C1 Answerable now

Working stream — we can analyze today

Points Registry and the event catalog already refresh regularly. Full answers where the ask fits Scored; partial when that scope is enough for the asker.

What we have

  • Points / placements / Competitor IDs after a point
  • Event catalog & scored landscape YOY
  • Reusable C1 work (e.g. division transitions)

Limits

  • Scored ≠ Entry / attendance / “held”
  • Partial must be labeled — not sold as total community
  • Invitational / no-shows not from registry alone

Quality on this layer

  • Less free-text drift; standardize entities
  • Refreshable tables: dancer · event · result
  • WSDC-layer quality work — not “whose database”

Ship now: progression / points structure · scored event landscape · champion paths & inactivity (with caveats).

C2 Exists — not in stream

Already in the WSDC contour — not yet joinable

Score Report / Sheets hold usable beginnings (often from ~2023). We can start designing how they enter the shared analytics stream next to C1.

What we already have

  • Event reports: tiers, counts by division / role
  • Competitors Lists — imperfect, but a trail exists
  • Same contour as rules §2.3 list requirements

Limits

  • Depth mostly ~2023 onward
  • No stable schema / retention / ID join yet
  • Cannot sit cleanly in the shared DWH/stream beside C1

Path → C1

  • Pipeline: ingest → clean → entities → join to C1
  • Geo / event-name aliases (Gap C)
  • Pre-2023 / missing archives → often C3 first, then C2

Competitors List is still early: scoring systems are the practical source to grow this block — current partial feeds stay C2 until joinable.

C3 Inside WSDC — not collected

We believe it lives in WSDC — we have not taken it yet

From Board asks: who to approach inside WSDC, what to request, whether it is obtainable. Often archive / enrichment for the same block as C2.

Typical gaps

  • Pre-2023 Score Report / list depth
  • Home city/state, official dates, AJP judge feeds
  • Fields that exist somewhere in ops — not in our stream

Work now

  • Map owner + format inside WSDC
  • Confirm: can we get it, under what policy?
  • Do not pretend it is already analytics-ready

Then promote

  • Found & collectable → C2
  • Pipeline + join → C1
  • Not findable / out of contour → rethink (C4 / park)
C4 Outside WSDC

Local WCS world — not the registry contour

Workshops, local dances, non-WSDC weekends, WCS population around events (e.g. JN-3c). Analytics here starts with collection design, not Points Registry extracts.

What it is

  • Community landscape beyond WSDC events
  • Venue radius / local population asks
  • Accuracy will not be registry-grade

How to organize

  • Start from existing community hubs (examples below), then fill gaps
  • Possible regional leads from other committees
  • Sector / region split + verification cadence; Board owner + mandate

Then

  • When a feed exists → C2
  • Committee advises schema — does not quietly own site / fees
  • Product / fee / hub policy → C5

Examples of already-centralized community listings (not WSDC, not registry-grade): weekenders.dance · westiehub.dance

C5 Scope / governance

Not a data pipeline question

Separate analytics and enablement from strategy, product, and policy — so the committee does not absorb the wrong work (Kay filter).

What it is

  • Priorities, mandate, mission stretch
  • Website / product features (e.g. rankings on site)
  • Fees, merge/delete, audit policy

Examples in this draft

  • Hub / education expansion ideas
  • NEA “ideas for analytics” as initiative framing
  • Listing fees, filter product calls

What we do

  • Return to Board / ops with a clear recommend
  • May advise with C1 evidence — not own the product
  • Does not climb C3 → C2 → C1

Process Workflow

From ask to track

  1. Intake — asker, text, must-have vs nice-to-have
  2. Decompose — one Board message → several atomic questions
  3. Classify — C1–C5 + population (Community / Entry / Scored)
  4. Respond — deliver (C1), partial + enabling step (C2/C3), collection design (C4), or scope return (C5)
  5. Track & reclassify when an enabling step ships
