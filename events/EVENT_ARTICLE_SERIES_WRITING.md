# Правила написания цикла «Портреты ивентов WSDC»

Документ фиксирует **редакторские принципы** серии. Методология данных (Skill JJ, gaps, метрики) живёт в workspace docs: `projects/wsdc/docs/events/EVENT_ARTICLE_NOTES.md`.

**Дизайн / shell:** новые draft и published article HTML — по [DESIGN_GUIDELINE.md](../docs/DESIGN_GUIDELINE.md) и [DESIGN_CHECKLIST.md](../docs/DESIGN_CHECKLIST.md) (chrome, tokens, article-shell, primitives).

Источник: редакторский разбор пилотной статьи про 4TH of July Convention  
([ChatGPT share](https://chatgpt.com/share/6a5f7f6a-ed10-83eb-bf1e-1e43f79f69a4)), плюс правки, согласованные при доработке пилота.

## Цель статьи

После чтения человек должен **в одном предложении** описать характер ивента.

Не цель: пересказать дашборд или выстроить рейтинг «кто круче».

Тест для автора: *«Чем этот ивент отличается от остальных?»*

Пример ответа для пилота: самый часто проводимый ивент в реестре, но не самый массовый; длинная история, точка входа для части танцоров, в основном разовые следы в поинтах.

---

## Storytelling (главное)

Слабая схема:

> график → описание → график → описание

Сильная схема:

> вопрос / вывод → доказательство (цифры, график) → следующий вопрос

Правила:

1. **Раздел начинается с вывода**, не с перечисления цифр.
2. Читатель должен **захотеть посмотреть график после текста**, а не наоборот.
3. После крупного блока полезен **короткий микровывод** (одна фраза), если он не дублирует заголовок.
4. Избегать ощущения «сопровождения дашборда»: данные раскрывают характер ивента, а не наоборот.
5. Интерпретация важнее нейтрального перечня. Не эмоции ради эмоций, а *что это значит*.

## Структура статьи серии

Типовой каркас (можно адаптировать под ивент, порядок смысловой):

1. **Лид серии** — зачем цикл, почему этот ивент первый/следующий.
2. **Intro** — происхождение / контекст + один главный контраст (например «самый старый ≠ самый большой»).
3. **Snapshot KPI** — цифры живут здесь; текст их не дублирует списком рекордов.
4. **Место среди других** (если есть сравнение) — вывод про характер, потом ранги, потом график.
5. **Как менялся ивент** — характер динамики, потом линия.
6. **Кто начинал здесь** — роль точки входа, KPI, дивизионы, имена.
7. **Как часто получают поинты** — разовость vs удержание год к году.
8. **Наиболее успешные** — лидеры ивента, график, пары/финалы.
9. **Summary** — синтез характера, не пересказ разделов.

Заголовки разделов должны отражать **смысл**, не метрику.  
Плохо: «Динамика метрик по годам», «Разнообразие танцоров».  
Лучше: «Как менялся ивент», «Как часто танцоры получают тут поинты».

---

## Открытие

- Сразу дать **рамку характера**, не оглавление «что рассмотрим».
- История клуба / появления ивента — коротко.
- Пиковые годы (max dancers / points / new) **не обязательно** в intro: их место в графике динамики или в snapshot.

---

## Графики

Для каждого графика перед публикацией:

- Нужен ли он вообще?
- Понятен ли без абзаца сверху?
- Отвечает ли на конкретный вопрос раздела?
- Не перегружена ли подпись?

Практика пилота:

- Подпись короткая, без лишнего «наведите на точку…», если это не критично для UX.
- В тултипах retention: **процент + абсолюты** (`N из M`), без бессмысленного YoY отклонения процента.
- В бар-чартах топа: **только число** рядом с именем; лидера можно подсветить (`is-focus`).
- Две доли на одном баре подписывать явно:  
  `865 · 63,4% танцоров набрали 39,4% поинтов`.

---

## Summary

Summary **не пересказывает** статью.

Он отвечает на вопрос: *какой это ивент по характеру?*

Хороший паттерн:

- чем ивент **не** является (не самый массовый / не самый «результативный»);
- чем **является** (стабильность, длинная история, роль входа, разовость следа и т.д.);
- одна фраза про место в истории WCS / сообщества.

## Язык и стиль

### Термины

- Базовое слово серии: **ивент** (не прыгать хаотично между «событие / мероприятие / турнир / конвенция», если нет причины).
- **Успешное участие** = год с поинтами Skill JJ в реестре (не полный attendance и не любой выход на паркет).
- В UI тогглах: **Участия**, не «Издания», если речь о годах с поинтами у танцора.
- Сокращать канцелярит:  
  «получили поинты в рамках Skill Level номинаций» → «получили поинты в Skill Level».

### Humanizer (минимум)

- Без длинных тире (`—` / `–`) в основном тексте; диапазоны лет: `2020-2021`.
- Не раздувать значимость: избегать «особая роль в развитии сообщества», «сочетание стабильности и традиций», «vital / pivotal / tapestry»-конструкций.
- Не начинать раздел с театрального «Удивительно, но…», если вывод и так сильный (по желанию автора).
- Меньше рекламных эпитетов («яркие танцоры настоящего времени» → проще: «известные танцоры сейчас»).

### Голос

Статья = аналитический портрет с авторской интерпретацией данных.  
Не пресс-релиз и не документация к графику.

## Чеклист перед публикацией

- [ ] Есть одно предложение «характер ивента».
- [ ] Каждый раздел начинается с вывода.
- [ ] Графики следуют за вопросом/выводом, а не наоборот.
- [ ] Нет дублирования одних и тех же цифр в тексте и snapshot без нужды.
- [ ] Summary = синтез, не оглавление.
- [ ] В футере ясно: реестр поинтов ≠ attendance.
- [ ] Термины едины; нет лишних длинных тире и пустой пафосности.
- [ ] Методика (пары, gaps, Skill JJ) согласована с `EVENT_ARTICLE_NOTES.md` и фактическим кодом статьи.
